1 Introduction

1.1 Purpose of the Data Dictionary

This Data Dictionary records the metadata of the Office Employee Management System: what each item of data
means, how it is structured and formatted, where it comes from, where it goes and which rules govern it. It does
not contain employee records or transactional data. It is intended to let a reader understand the data of the project
without opening the original diagrams.

The dictionary is derived strictly from the two source documents of Group 2: the requirements specification
(Assignment 2: functional requirements, non-functional requirements and use case diagram) and the data flow
diagrams (Assignment 3: Level 0 and Level 1, with the Level 2 diagrams drawn from them). Where those
documents do not specify a property, such as a field length or an allowed value list, the property is labelled
Proposed. Where the documents state or clearly imply an item, it is labelled Confirmed or shown as named in
the source.

1.2 Scope of Documentation

The dictionary covers five external entities, 33 processes (one at Level 0, 7 at Level 1 and 25 at Level 2), 7 data
stores, every data flow found in the Level 0, Level 1 and Level 2 diagrams, the 53 data structures and 97 data
elements carried by those flows, a logical database proposal, business rules, security metadata, traceability
matrices and a consistency audit of the source documents.

1.3 Project Overview

The Office Employee Management System is intended to centralise employee-related information and routine
human-resource, recruitment, attendance, leave, payroll, salary and reporting activities. It supports role-specific
access so that each actor can perform only the operations relevant to that role.

1.4 Objectives

The objectives are: (1) to define every data flow, store, structure and element in a consistent vocabulary; (2) to
trace each item to use cases, functional requirements and non-functional requirements; (3) to separate confirmed
documentation from proposed design; and (4) to report inconsistencies in the source documents without silently
correcting them.

1.5 System Description

Five actors use the system: Employee, HR Manager, Recruitment Officer, Payroll Officer and Finance Manager.
The system covers 18 use cases (UC-01 to UC-20, without UC-08 and UC-18, which were removed), 18
functional requirements and 20 non-functional requirements. The Level 1 diagram divides the system into Manage
Attendance (0.1), Manage Leave (0.2), Manage Employee Records (0.3), Manage Recruitment (0.4), Manage
Payroll (0.5), Generate Payslips (0.6) and Generate Reports (0.7). Seven data stores, D1 to D7, hold the persistent
data.

1.8 Conventions

Identifiers. EE-nn external entity; D1 to D7 data stores; processes keep their diagram numbers; DF-nnn data
flow; DS-nn data structure; DE-nnn data element; T-Dx-nn proposed table; BR-nn business rule; L0-nn and L1-nn
register entries for diagram arrows. UC, FR and NFR identifiers are those of the source.

Data flow identity. A logical data flow keeps one DF identifier across levels. Its Level 1 and Level 0
representations are shown by register references. Level 0 and Level 1 arrows that carry several flows are
decomposed in the registers of Section 3.

Notation (Section 6). = consists of; + and; [ ] optional; { } repetition; ( ) grouping; | alternative.

Pairing assumption. NFR-n is read as the quality requirement attached to FR-n because the source lists them in
pairs; NFR-21 and NFR-22 apply to all functional requirements. UC-n relates to FR-n.

Directions. Flow directions follow the arrowheads in the diagrams. Where an arrow contradicts its label or
another level, the Level 2 direction is used in the catalogue and the difference is reported in Section 12.

authentication items of Level 0 noted in the register.
