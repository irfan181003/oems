# Office Employee Management System — Backend (Group 02)

REST API for the *Office Employee Management System* (Software Engineering project, implementation phase Gr_02_Imp1).
It implements the design fixed in:

- `docs/Group02_Assign2_Revised_v3.pdf` (text copy `docs/requirements.txt`) — 18 use cases, FR-1…FR-20, NFR-1…NFR-22, 5 actors
- `docs/Group02_Assign3.2_updated.pdf` (text copy `docs/dd.txt`) — DFD levels 0–2 and the Data Dictionary (D1–D7, 10 tables, BR-01…BR-30)
- `docs/BACKEND_PROMPT.md` — the build specification

Not implemented, because Assignment 2 removed them: the Director actor, UC-08 View Organizational Records and UC-18 Organization Summary Report. FR-8 and FR-18 do not exist.

See `TRACEABILITY.md` for the mapping endpoint → UC → FR → process → BR → NFR → tables, and `api.http` for one example request per endpoint.

## Stack

Node.js ≥ 20 (developed and tested on Node 26) · Express 4 · SQLite through `better-sqlite3` (foreign keys on, parameterised SQL only, no ORM) · `zod` 4 validation · `bcryptjs` · `helmet` · `cors` · `express-rate-limit` · `pdfkit` (payslip PDF) · `morgan`. Tests use the built-in `node --test` runner with `supertest`. CommonJS throughout.

## Setup and run

```bash
cd backend
npm install            # better-sqlite3 downloads a prebuilt binary (allowed in package.json "allowScripts")
cp .env.example .env   # then edit if needed
npm run seed           # creates data/oems.db with demo data (safe to run again)
npm start              # API on http://localhost:4000/api
npm test               # full test suite (in-memory database, does not touch data/oems.db)
```

`npm run dev` restarts on file changes. To start from scratch, stop the server, delete `backend/data/` and run `npm run seed` again.
`.env`, `node_modules/` and the database file are git-ignored.

## API conventions

- Base path `/api`. Send `Authorization: Bearer <token>`; the token comes from `POST /api/auth/login`.
- Every response uses the DS-04 *Operation Result* envelope:
  `{ "result_status": "Success" | "Failed", "reference_id", "response_message", "error_message", "data" }`.
  Validation failures also include `details: [{ field, message }]`.
- Status codes:

  | Code | When |
  |---|---|
  | 400 | Fields that are not allowed, or malformed JSON |
  | 401 | Not logged in, or the session expired |
  | 403 | Role not permitted (always written to `AUDIT_LOG` as `Denied`) |
  | 404 | Record not found |
  | 409 | Duplicate or state conflict |
  | 422 | Field rule failed |
  | 429 | Too many login attempts |

  Stack traces are never returned.
- Dates use the format `YYYY-MM-DD`, times `HH:MM` (DE-005, DE-006, DE-060; interview times may be sent as `HH:MM:SS` and are stored as `HH:MM`) and pay periods `YYYY-MM`. Money is INR with 2 decimals. Internally all money is computed in integer paise.
- IDs are always generated by the server, in the Data Dictionary §7 formats (`EMP00001`, `ATT000000001`, `LV00000001`, `VAC00001`, `CAN00001`, `INT0000001`, `OFR0000001`, `PAY000000001`, `PS0000000001`, `RP000001`).
- Restricted data is never written to `AUDIT_LOG` and never returned to roles that may not see it: salary, bank account, retirement contribution and nominee, offered salary, passwords and tokens.

## Salary calculation (UC-12, BR-17 — Proposed)

`src/modules/payroll/calculator.js` is a pure function: no database, clock or randomness. The same inputs always give the same result (BR-16). It works in integer paise and rounds half-up on each line:

```
unpaid_absence   = max(0, working_days − days_present − paid_leave_days)
earned_basic     = basic × (working_days − unpaid_absence) / working_days
gross            = earned_basic + allowances
pf               = 12 % of earned_basic
tax              = 0 % if gross ≤ 25,000 · 5 % if ≤ 50,000 · 10 % above   (flat rate of the slab)
total_deductions = tax + pf + other_deductions
net              = gross − total_deductions        (negative → that employee fails, the run continues)
```

- `days_present` counts `Present` attendance in the month.
- `paid_leave_days` counts Approved Casual/Sick/Earned leave days that fall in the month. Leave that crosses a month boundary is trimmed to the month (BR-18).
- PF %, the tax slabs and the paid leave types are in `src/modules/payroll/rules.js` (see A-6).

## Assumptions and deviations

These are the documented decisions where the source documents are silent or contradictory. Each one is marked `ASSUMPTION A-n` in the code.

| # | Where the documents are silent or conflict | Decision |
|---|---|---|
| A-1 | Data Dictionary §8 marks *every* FK column "UNIQUE: Yes", which would allow e.g. one attendance row per employee ever | Composite uniqueness instead: ATTENDANCE (employee_id, att_date) · PAYROLL (employee_id, pay_period) · PAYSLIP (payroll_id) · RETIREMENT_PLAN (employee_id) · OFFER (candidate_id) · INTERVIEW_SCHEDULE (candidate, date, time) and (venue, date, time). Interview slots are partial unique indexes that ignore `Cancelled` interviews, so a cancelled slot can be booked again; venues are compared case-insensitively. LEAVE_APPLICATION and CANDIDATE have no extra uniqueness. One retirement plan per employee is kept as in §8. |
| A-2 | Authentication has no process or store (§12 #3 recommends "Manage User Access") | Supporting tables `USER_ACCOUNT` and `SESSION` (not part of D1–D7). Opaque 32-byte tokens; only their SHA-256 is stored. Passwords use bcrypt (cost 10). Registering an employee creates an `Employee` account with a one-time temporary password, returned once. Other roles exist only through the seed. An account with `is_active = 0` cannot log in. |
| A-3 | No flow creates candidates (§12 #10) | `POST/GET /candidates` for the Recruitment Officer; the vacancy must exist and be Open. |
| A-4 | Level 0 shows Payslip/Salary to the Employee, but no Level 1/2 flow does (§12 #9) | `GET /salary/me` and owner read access to `/payslips/:id` and `/payslips/:id/download`. |
| A-5 | BR-26 "Denied and logged" and NFR-4/7/20 traceability, but no audit store | Supporting table `AUDIT_LOG`. It records every denied request, every successful create/update/decision (in the same transaction), and every refused create/update/decision (outcome `Failed`). Values of restricted fields are never logged, only field names. |
| A-6 | BR-17 formula is Proposed; tax and PF are not specified; DE-081 counts "loss of pay" in Total Deductions *and* BR-17 already reduces Gross (double count) | Follow BR-17: loss of pay appears in gross only, and `total_deductions = tax + pf + other_deductions`. Constants live in `payroll/rules.js` ("Proposed — not specified in sources"). PAYROLL has no column for other deductions, so it is implied as `total_deductions − tax_deduction − pf_deduction`; the payslip shows it that way. Approved `Unpaid` leave counts as unpaid absence. |
| A-7 | Assignment 2 gives the self-service use cases (UC-01, UC-02 own, UC-03, UC-05, UC-11 own) to the *Employee* actor only | `SELF_SERVICE_ROLES` (default `Employee`). Self-service routes always act on the logged-in user's own record and reject any employee ID from the client. |
| A-8 | "Must be an existing department" (DE-035), but no list is given | Fixed list in `src/lib/departments.js`: HR, Finance, Engineering, Sales, Operations, Recruitment, Payroll. |
| A-9 | Assignment 2 links UC-12/13/14 to no actor and lets the Payroll Officer only *view* salary and payroll records; the DFD (DS-31 Payroll Input Data from the Payroll Officer) has the Payroll Officer drive Process 0.5/0.6 | Following BACKEND_PROMPT §4/§6, the Payroll Officer runs payroll, changes payroll status and generates payslips. |

### Further implementation decisions

The documents leave these open. Each is the narrowest reading that satisfies the rules.

1. **Rules repeated in the database.** CHECK constraints repeat three rules that the services also enforce:
   - check-out later than check-in (BR-02);
   - leave end on or after start (BR-05);
   - positions ≥ 1 (BR-12).

   SQLite's `CURRENT_DATE` defaults are UTC, so the application always supplies dates itself (in APP_TIMEZONE).
2. **Attendance.** Check-in and check-out times are stored as `hh:mm` (DE-005, DE-006), and the database rejects any other format. Because BR-02 requires check-out to be *later*, a check-out in the same minute as the check-in is refused. Only `Present` rows are ever written. `Absent`, `Half-day` and `On Leave` are allowed by the schema, but no documented process creates them. DE-005 "check-in within the working day" is not enforced, because no working hours are defined.
3. **Leave.**
   - A leave may start on the applied date (today).
   - `leave_days` counts calendar days.
   - Overlapping applications are not blocked, because no rule exists.
   - `GET /leaves/:id` is open to the HR Manager or the owner.
4. **Profile and employee updates.** Fields other than contact number, e-mail and address are refused with 400 (BR-08 allows "ignored or refused"). E-mail uniqueness ignores letter case. Changing DOB or joining date re-checks the 18-years-at-joining rule.
5. **Vacancies.** `PATCH /vacancies/:id` may set `Open` or `On Hold`; closing goes through `POST /vacancies/:id/close`.
6. **Interview and offer status changes.** These have no ordering rules ("Domain validation only", DE-067 and DE-073).
7. **Offers.** An offer needs the candidate's *latest* interview (by date, time, ID) to be `Selected`. The offered position always comes from the vacancy's job title. The offer letter's salary label is just "Offered salary", because the documents do not say whether it is monthly.
8. **Payroll runs.**
   - Resigned/Retired or unknown employees named in `lines` are reported as `failed`.
   - Without `lines`, all Active employees are processed.
   - The run's `status` is `Processed` if at least one line was stored, otherwise `Nothing processed`.
   - `PAYROLL.leave_days` stores paid leave days.
   - Status changes are Processed → Paid and Processed ↔ On Hold; Paid is final.
9. **Payslips.**
   - `payslip_count` = payslips available for the request (new + existing).
   - The payslip shows *earned basic* (gross − allowances), so the earnings rows add up to gross; the monthly basic is shown in the header.
10. **Reports.**
    - Every HR report type needs a valid `from_date … to_date` period (BR-22 "Role HR Manager; valid period"). Headcount and Employee reports describe the current employees; the period appears in the report title.
    - The financial report includes pay periods whose month falls within `from_date … to_date`.
    - The `Payroll` type lists each line; `Financial` gives totals only.
    - Departments are the employee's current department.

### Open questions for the team

1. Should setting `employment_status` to Resigned/Retired also disable the user's login? It currently does not, because the documents are silent.
2. Should check-in be limited to working hours (DE-005 "within the working day")? If so, what are the hours?
3. If `SELF_SERVICE_ROLES` ever includes `HR Manager`, should an HR Manager be prevented from deciding their own leave?
4. Should interview and offer status changes follow a fixed order (e.g. Issued → Accepted/Declined only)?
